# CLAN WAR 2.0 — спецификация

CLAN WAR 2.0 является единственной системой клановых войн в проекте.
Старая механика захвата арен удалена из handlers, services, admin UI, фоновых задач и базы данных.
Все активные данные режима хранятся только в таблицах `war2_*`.

## 2. Draft System

`app/services/war2_draft.py`. 24 CARD POOL: 3 GK + 6 DEF + 15 FWD, только из
коллекций с `collections.is_exclusive = 0` (BASE_COLLECTION). Пул снапшотится в
`war2_draft_pools.card_ids_json` в момент генерации — дальнейший драфт стабилен, даже
если позже поменяется состояние живых `cards`. Snake Draft: раунд 1 — игрок, затем
соперник; раунд 2 — соперник, затем игрок; и т.д., до 6 карт с каждой стороны (3 FWD / 2 DEF / 1 GK).
Сохраняются pool (`war2_draft_pools`), picks (`war2_draft_picks`, с `UNIQUE` на
дубли), порядок (`round_number`/`pick_order`), итоговый состав читается из picks
(`finalize_lineup_for`).

**Решение: драфтит интерактивно только инициатор матча.** В проекте нет ни одного
примера синхронного взаимодействия двух живых Telegram-сессий (даже
`play_player_match` мгновенно симулирует оба сохранённых состава без ожидания) —
строить такое было бы отдельной параллельной системой, ровно то, что просили не
делать ("максимально переиспользовать старый код"). Соперник добирается
`auto_pick_for_opponent()` — эвристика (сначала непокрытая позиция, иначе лучший OVR)
сразу после каждого пика игрока, в той же snake-последовательности.

## 3. CLONE_WAR

`war2_modes.build_clone_war_lineup()`: без Draft — один случайный набор из 6 карт (3 FWD / 2 DEF / 1 GK)
Base Collection, OVR 92-99, **одинаковый для обеих сторон**. `war2_draft_pools`/
`war2_draft_picks` не создаются (`war2_matches.pool_id` остаётся NULL). Сгенерированный
состав сохраняется в `war2_matches.user_lineup_json`/`opponent_lineup_json` сразу на
экране подтверждения — иначе на шаге записи результата был бы сгенерирован уже
ДРУГОЙ случайный набор, отличный от показанного игроку.

## 4. SALARY WAR

После Draft — `war2_modes.validate_salary_cap()`: сумма `cards.salary` пяти выбранных
карт против лимита (`WAR2_SALARY_CAP = 50000`, тысячи $ — тот же формат хранения, что
у `LEAGUE_SALARY_CAPS`/`STRONGHOLD_SALARY_CAP`, т.е. 50000 = $50 000 000, НЕ буквальные
`50_000_000`). Лимит дублирован в `game_settings.war2_salary_cap`, чтобы админ мог
подправить без деплоя (`get_effective_salary_cap()` читает настройку, с константой как
дефолтом). Превышение блокирует подтверждение состава с точным текстом суммы через
`format_salary()` (тот же форматтер, что и у остальных зарплатных лимитов бота).

## 5. WILD CARD

После обычного Draft — `war2_modes.apply_wild_card_replacement()`: замена ровно ОДНОЙ
выбранной карты на любую карту **из собственной коллекции игрока** (реальная
`user_cards` строка, без ограничения по OVR/редкости — буквально по тексту ТЗ).
Ограничения: одна замена (`war2_matches.used_wild_card` + `UPDATE ... WHERE
used_wild_card = 0`, транзакционно — вторая попытка отклоняется на уровне БД, не
только в UI), только текущий матч (исходные `war2_draft_picks` не трогаются — замена
живёт только в `war2_matches.wild_card_*` и в эфемерном ростере, который уходит в
симуляцию).

## 6. War Roulette

`war2_modes.roll_active_mode()` — см. раздел 1, пункт 4.

## 7. Collection System

`collections.is_exclusive` — новая аддитивная колонка (`ensure_column` в
`db.py:run_migrations()`, по умолчанию `0`). BASE_COLLECTION (`is_exclusive=0`) —
источник Draft Pool и Clone War. EXCLUSIVE_COLLECTION (`is_exclusive=1`) — Packs/
Inventory/Wild Card. `war2_seed.py` помечает эксклюзивными `the_stronghold` и
`clan_war2_legends`. **`free-cards` НЕ эксклюзивна** — это и есть базовая коллекция,
из которой пополняется Draft Pool/Clone War (в проде наполняется контентом админов
через уже существующий `admin_cards.py`, в тестовой/demo среде — см. раздел 12).
Любая новая коллекция, которую создаст админ в будущем, по умолчанию `is_exclusive=0`
(доступна для дро-пула), если явно не помечена иначе.

## 8. CLAN WAR LEGENDS

Коллекция `clan_war2_legends` (16 карт: Zetterberg 98, Kopitar 98, Stone 97, Point 97,
O'Reilly 96, Aho 96, Slavin 96, Forsberg 95, Zibanejad 95, Demko 95, Thomas 94,
Boeser 94, Meier 94, Sergachev 93, Seider 93, Saros 93) создаётся через
**существующую систему коллекций** — `app/services/war2_seed.py`, идемпотентный
upsert-по-коду/upsert-по-`(player_key, overall, collection_id)`, скопированный по
образцу `app/services/stronghold_seed.py` (тот же паттерн, которым в проекте уже
создана коллекция THE STRONGHOLD). Ничего не хардкожено мимо таблиц `collections`/
`cards` — карты видны и управляются через тот же `admin_cards.py`, что и любые
другие карты бота.

## 9. Pack System

`CLAN_WAR_PACK_LEVEL_1/2/3` (1/2/3 карты Legends соответственно) — через
**существующую** систему паков: `packs`/`pack_slots`/`pack_cards`, `pack_slots` без
фильтров по коллекции/редкости (значения `NULL` — `select_random_card()` в
`packs.py` их просто пропускает), `pack_cards` содержит ровно 16 id карт Legends на
каждый из трёх паков. Открытие паков (`open_user_pack()`) не изменено ни на строку —
новые паки работают через полностью существующий код.

## 10. Inventory: FRAME / BACKGROUND / NICK_BADGE

Новых аналогов в проекте не было (проверено: единственный похожий паттерн —
`creator_bank_items`, но это одноразовый payout-ledger креаторов, не экипируемый
инвентарь). Реализовано двумя новыми таблицами, зеркалирующими уже существующий
паттерн `cards`/`user_cards` (каталог/владение):

- `war2_cosmetic_items` — каталог (админ создаёт: тип, код, название, редкость,
  картинка/текст приставки).
- `user_cosmetic_items` — владение, **future-market-ready поля прямо на строке
  владения**: `id`, `owner_id`, `type`, `rarity`, `created_at`, `source` — раздел
  "FUTURE MARKET READY" ТЗ буквально выполнен (готово для будущего Black Market/
  Trade/Auction: type/rarity денормализованы на строку владения именно для того,
  чтобы такие системы могли фильтровать/сортировать без join). "Экипирован только
  один предмет на тип" — в коде транзакцией (снять `equipped` с братьев по типу,
  затем поставить новому), не через частичный уникальный индекс/триггер — в проекте
  такой техники нигде не используется, не стал вносить новую.

## 11. Frame / Background / Nick Badge — рендер

`app/services/renders.py`: `_load_background()` и `_paste_shadowed_card()` получили
новые опциональные параметры (`override_path`/`frame_override_path`), которые по
умолчанию `None` — **существующие вызовы без новых аргументов дают то же
изображение, байт-в-байт** (проверено тестом `test_render_lineup_image_unchanged_...`).
Новая функция `render_war2_lineup_image()` — **отдельная**, не расширение
`render_lineup_image()`: у CLAN WAR 2.0 состав из 6 карт в тех же слотах, что обычный состав: 3 FWD / 2 DEF / 1 GK
(`LINEUP_SLOT_ORDER` — это 6-слотовая G/D1/D2/F1/F2/F3 система обычного лайнапа,
для драфтового ростера она не подходит по конструкции). Переиспользованы все
примитивы компоновки как есть: `_load_background`, `_card_size`,
`_paste_shadowed_card`, `_font`, `cleanup_render_cache`. `_draw_nickname_badge()` —
тот же rounded-rect+text приём, что и у `_draw_ovr_text`.

**Осознанно не сделано**: вкрутить `format_nickname_with_badge()` во все места, где
где-либо в боте показывается ник (профиль, лидерборды, сообщения о найденном матче).
Функция чистая и подключается по одному месту за раз — сделано только там, где явно
нужно для CLAN WAR 2.0 (экран результата матча). Расширение на остальной бот
оставлено на будущее как отдельная, самостоятельная по объёму задача.

**Осознанно не сделано**: подключение косметики к существующим экранам обычного
лайнапа (`app/handlers/lineup.py`/`matches.py`, которые тоже вызывают
`render_lineup_image()`). Причина: там `user_id` в коде — это **Telegram ID**
(`target.from_user.id`), а `war2_cosmetics.get_equipped_*` ожидает внутренний
`users.id` — бездумная вставка вызова была бы реальным риском (неверный/несуществующий
владелец предметов), а корректная правка (резолвить внутренний id) требует более
внимательного прохода по этим экранам, чем оправдано для опциональной "плюшки" в
рамках уже очень большой задачи. `render_lineup_image()` уже поддерживает нужные
параметры — подключение тривиально сделать отдельным, небольшим проходом позже.

## 12. Admin Panel

`app/handlers/admin_war2.py` (+ `app/states/admin_war2.py`): сезон (запуск на
4 недели/`game_settings.war2_season_length_days`, завершение — статистика не
удаляется), режимы (on/off по `war2_modes.active`, без деплоя), косметика
(создать/изменить активность/удалить(soft)/выдать игроку — паттерн "lookup по
telegram_id -> подтверждение", скопированный с `stronghold_admin.py:
grant_compensation` + `admin_stronghold.py`). Загрузка PNG для FRAME/BACKGROUND —
тот же паттерн, что `admin_cards.py:save_card_image()` (фото или документ-картинка,
`assets/uploads/war2_frames`/`war2_backgrounds`). Паки/коллекция Legends отдельных
экранов не получили — управляются полностью существующими `admin_cards.py` и
Packs-админкой (коллекция обобщена по `collection_id`, паки по `pack_id`), это и есть
"reuse existing admin flows" по факту, а не отдельная реализация. Билеты/зарплатный
лимит — существующие `game_settings` (`war2_daily_tickets`, `war2_salary_cap`),
редактируются в общем экране настроек, копия здесь не создавалась. Ростер клана
(раздел 20) сюда сознательно НЕ входит — это решение уровня клана (кто из 5 играет),
им управляет лидер/офицер конкретного клана в игровом экране `war2:roster`, а не
глобальный администратор бота; общий лимит размера ростера (`war2_roster_size`) при
этом всё равно настраивается централизованно через `game_settings`.

Права: `PERMISSION_WAR2` (новая, только добавления в `admin_permissions.py`) —
выдана ролям `ADMIN_ROLE_CLAN` и `ADMIN_ROLE_ECONOMY`, `admin_war2:`/`admin_war2cos:`
зарегистрированы в `CALLBACK_PERMISSION_PREFIXES`. Ни одна существующая роль/префикс
не изменены.

Вход в игровой экран — кнопка "⚔️ CLAN WAR 2.0" в меню кланов
(`app/keyboards/community.py:build_clans_main_keyboard`, рядом с существующей "🏟 Войны
кланов"). Вход в админку — кнопка "🛠 Админка CLAN WAR 2.0" на этом же экране, видна
только `is_admin()` (тот же паттерн, что у THE STRONGHOLD: `stronghold.py` показывает
ссылку на `admin_stronghold.py` так же, не через общее меню `admin_panel.py`).

## 13. База данных

Все изменения — **новые таблицы** (`CREATE TABLE IF NOT EXISTS`, добавлены в
`app/database/schema.py:SCHEMA_QUERIES`, ничего существующее не тронуто) плюс ровно
**одна** аддитивная колонка (`collections.is_exclusive`, через `ensure_column()` в
`db.py:run_migrations()`). Ни одна существующая таблица не изменена структурно, ни
одна строка данных не удаляется никаким новым кодом. `users`/`cards`/`collections`/
`inventory` (=`user_cards`/`user_packs`)/`rewards`-таблицы читаются, но не пишутся
никаким новым кодом за пределами штатных операций (выдача карты через Wild Card
только ЧИТАЕТ `user_cards`, никогда не пишет).

## 14. Расхождения с планом / осознанные упрощения

- **Тексты/клавиатуры инлайн в `app/handlers/war2.py`/`admin_war2.py`**, а не в
  отдельных `app/keyboards/`/`app/texts/` файлах, как изначально предлагал план. Из
  двух живых прецедентов в проекте (чистое разделение у `admin_cards.py` и монолит у
  `admin_stronghold.py`) выбран монолит — ради единого обзора всего flow при таком
  количестве экранов и заданном объёме сессии. Не мешает будущему рефакторингу.
- **Нет отдельных `app/states/war2.py`** для игрового флоу: весь прогресс матча уже
  в БД (`war2_matches`/`war2_draft_picks`), а `match_id` передаётся через
  `callback_data`, а не через FSMContext — что даёт восстановление после рестарта
  бота даром (кнопка на старом сообщении рабочая), без необходимости в States вообще.
  Для админки (многошаговый ввод текста/файла) States использованы —
  `app/states/admin_war2.py`.
- **Тестов уровня хендлеров (через настоящие aiogram CallbackQuery/Message, не
  дак-тайпинг) в проекте раньше не было нигде** — даже "smoke"-тест THE STRONGHOLD
  (`tests/test_stronghold_handlers_smoke.py`) тестирует только чистые `build_*`-
  функции, возвращающие `(текст, клавиатура)`, а не сами Telegram-объекты
  (`safe_edit_message()` делает `isinstance(message, Message)`, дак-тайпинг тут не
  прошёл бы). Добавлен новый файл `tests/test_war2_handlers_smoke.py` (7 сценариев) —
  конструирует настоящие `User`/`Chat`/`Message`/`CallbackQuery` (минимальный набор
  обязательных полей), подменяет только сетевые методы отправки
  (`Message.edit_text`/`answer`/`answer_photo`, `CallbackQuery.answer`) на no-op, и
  вызывает реальные функции-хендлеры напрямую — весь путь main → start → draft →
  confirm → result, Clone War, Wild Card, отмена, косметика, ростер, редрафт
  последнего раунда, админ-экраны (сезон/режимы/создание косметики через FSM). **Этот
  файл поймал три реальных бага до того, как их увидел бы игрок** — см. раздел 19.

**Три пункта ниже были в первой версии этого отчёта отмечены как "осознанно
отложено" — по прямому запросу пользователя ("делай всё, что осталось") реализованы
в этом же заходе:**

- **"Clan size: 5" — реализовано.** Новая таблица `war2_clan_roster` (раздел 20),
  `clan_members`/`CLAN_MAX_MEMBERS=10` остаются общей системой участников клана —
  ростер лишь ОТМЕЧАЕТ, кто из уже существующих участников клана допущен играть
  CLAN WAR 2.0, поверх, а не вместо `clan_members`. `start_war2_match()` теперь
  требует: клан есть, ростер клана не пуст, игрок в ростере — иначе понятная ошибка
  с указанием, что делать (`NO_CLAN`/`ROSTER_NOT_SET`/`NOT_ON_ROSTER`). Подбор
  соперника (`find_war2_opponent`) тоже сужен до рострированных игроков других
  кланов — иначе "5 участников с одной стороны" не имело бы смысла, если соперником
  мог стать произвольный, не выбранный в ростер участник чужого клана.
- **Косметика в обычных экранах лайнапа — реализовано.** `app/handlers/lineup.py:
  send_lineup_view()` получил параметр `player_id` (внутренний `users.id`, в отличие
  от локальной переменной `user_id` в этой функции, которая на самом деле telegram_id
  и использовалась только для имени файла) — оба вызывающих места (`show_lineup`,
  `lineup_button`) теперь передают `profile.id`. `app/handlers/matches.py:
  send_match_lineup_previews()` не требовал такой правки: `MatchPlayResult.user_id`/
  `opponent_user_id` там УЖЕ являются внутренними id — подключены напрямую через
  новый хелпер `_equipped_war2_cosmetics()` (best-effort, никогда не бросает).
- **SALARY_WAR: пересдача раунда — реализовано** (`war2_draft.redo_last_round()`).
  Не "точечная пересдача одной карты", как упоминалось как вариант: при превышении
  лимита удаляются ОБА пика последнего (5-го) раунда — и игрока, и соперника, не
  только игрока. Причина: `get_draft_state()` вычисляет `current_round`/
  `current_picker` из ОБЩЕГО количества пиков в таблице, а не из порядкового номера
  конкретной строки — удаление только пика игрока при уже вставленном пике
  соперника в том же раунде рассинхронизировало бы этот счётчик и сломало бы
  порядок snake draft на всех следующих матчах с той же логикой. Откат целого
  раунда — минимальное изменение, которое не нарушает инвариант. После пересдачи
  соперник вновь добирается `auto_pick_for_opponent()` как обычно.

## 15. Тесты

`tests/test_war2.py` (18 сценариев, сервисный слой): билеты (исчерпание + сброс по
новому дню), квоты позиций Draft Pool + только BASE_COLLECTION, snake draft (порядок
+ запрет повтора), CLONE_WAR (идентичный состав), SALARY_WAR (блокировка
превышения + пересдача последнего раунда), WILD_CARD (одна замена + запрет
повторного использования + оригинальные пики не тронуты), полный матч (результат
пишется только в `war2_*`, `users`/`clans` не меняются — ключевая регресс-проверка),
паки Legends (выдают только карты нужной коллекции, верное количество по уровню),
косметика (grant → equip → get_equipped_*, вытеснение того же типа), сезон
(длительность, статистика не удаляется при завершении), рендер (`render_lineup_image`
без новых аргументов не меняется + `render_war2_lineup_image` не падает на составе с
заменой Wild Card), ростер (добавление/удаление/лимит 5, только лидер/офицер, только
участник клана, `start_war2_match` блокирован без клана/ростера, подбор соперника
сужен до рострированных).

`tests/test_war2_handlers_smoke.py` (10 сценариев, реальные aiogram-объекты, см.
раздел 14): main/start-экраны, полный Draft через хендлеры (SALARY_WAR) до
подтверждения и результата, Clone War через хендлеры, Wild Card через хендлеры,
отмена + косметика (список/экипировка), ростер (добавить/убрать через хендлеры,
экран без клана не падает), пересдача последнего раунда SALARY_WAR через хендлер,

## 19. Три реальных бага, найденных ТОЛЬКО хендлер-тестами (не сервисными)

Сервисный слой был написан и покрыт тестами первым и полностью проходил (раздел 15,
`tests/test_war2.py`) — но эти тесты вызывают `war2_draft.generate_draft_pool()` и
другие сервисные функции напрямую, в обход хендлеров. Хендлер-тесты
(`tests/test_war2_handlers_smoke.py`), прогоняющие тот же флоу ЧЕРЕЗ реальные функции
`app/handlers/war2.py`, нашли три бага, которых сервисные тесты в принципе не могли
поймать:

1. **Пул Draft нигде не генерировался в реальном пути запуска матча.**
   `war2_core.start_war2_match()` создавал строку `war2_matches`, но
   `war2_draft.generate_draft_pool()` не вызывался ни в хендлере, ни в сервисе —
   только тестовые хелперы вызывали его явно перед тем, как разыгрывать драфт.
   Любой реальный игрок в режиме SALARY_WAR/WILD_CARD получил бы экран Draft с
   пустым пулом (`IndexError` при попытке хендлера показать карты на выбор — то есть
   реальный краш экрана в проде на первом же шаге после War Roulette). Исправлено:
   `generate_draft_pool()` теперь вызывается внутри `war2_core.start_war2_match()`
   сразу после создания строки матча, если `mode.uses_draft` — то есть на уровне
   сервиса, а не хендлера, поэтому пул гарантированно есть для ЛЮБОГО вызывающего
   кода, не только Telegram-хендлера.
2. **`CallbackQuery.data` — замороженное pydantic-поле в используемой версии
   aiogram.** Хендлер экипировки косметики (`war2_cosmetics_equip`) пытался
   переиспользовать экран списка через `callback.data = f"war2:cos:{type}"` — в рантайме
   это `pydantic_core.ValidationError: Instance is frozen`, то есть реальный краш при
   нажатии "Экипировать" для любого предмета. Исправлено: экран списка вынесен в
   отдельную функцию `_render_cosmetics_list()`, которую вызывают оба хендлера
   напрямую, без попытки мутировать callback.
3. **Хендлер `war2_roster` и локальный `from app.services import war2_roster`
   внутри него — одно и то же имя.** Функции добавления/удаления из ростера делали
   `from app.services import war2_roster` (сервис) внутри тела функции, а в конце —
   `await war2_roster(callback)`, рассчитывая вызвать хендлер-функцию с тем же именем
   на уровне модуля. Локальный импорт затирает внешнее имя на всё тело функции — в
   рантайме это `TypeError: 'module' object is not callable`, то есть реальный краш
   при каждом нажатии "➕ Добавить игрока"/"❌ Убрать" в ростере. Исправлено:
   хендлер-функция переименована в `war2_roster_screen` — коллизия с именем
   сервисного модуля `war2_roster` устранена окончательно (а не только в паре мест).

Все три бага были бы невидимы для сервисных тестов и обнаружились бы только вручную в
Telegram — ровно тот класс регрессии, для которого написан этот файл (see also
`tests/test_stronghold_handlers_smoke.py`'s docstring про тот же урок на THE STRONGHOLD).

## 20. Ростер клана (`war2_clan_roster`)

Таблица `war2_clan_roster(clan_id, user_id, added_by_user_id, created_at)`,
`UNIQUE(clan_id, user_id)` — НЕ переиспользует и не меняет `clan_members` (общую для
всего бота), только отмечает, кто из уже существующих
участников клана допущен играть CLAN WAR 2.0. Управление — `app/services/
war2_roster.py`: `get_clan_roster`, `add_roster_member`/`remove_roster_member`
(только `role IN ('leader','officer')` в этом клане, `War2Error("ROSTER_NOT_MANAGER")`
иначе), лимит — `game_settings.war2_roster_size` (по умолчанию 5).

Экран `app/handlers/war2.py:war2_roster_screen` (`war2:roster`) — список текущего
ростера, для лидера/офицера кнопки добавить/убрать; экран добавления
(`war2:roster_add:<page>`) листает `clan_members`, ещё не в ростере.

`war2_core.start_war2_match()` теперь ЖЁСТКО требует (раздел 1 обновлён): игрок
состоит в клане (`NO_CLAN` иначе), у клана есть непустой ростер (`ROSTER_NOT_SET`
иначе — направляет к лидеру/офицеру), игрок в этом ростере (`NOT_ON_ROSTER` иначе).
`find_war2_opponent()` тоже ищет только среди `war2_clan_roster` других кланов, не
среди всех `clan_members` — иначе ограничение "5 игроков с одной стороны" не имело бы
смысла, если соперником мог стать не выбранный в ростер участник чужого клана.
